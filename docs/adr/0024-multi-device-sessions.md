# ADR-0024: Multiple device sessions per user, listed and closable by their owner

## Status

Accepted — 2026-11-17. Extends ADR-0002 (device-bound sessions) and ADR-0023 (refresh cookie,
reuse detection).

## Context

ADR-0002 binds every session to a client-generated device id, but `user_devices.user_id` was
`unique`. Each user therefore had exactly one session row. A login from a second browser
overwrote the first one's device id, fingerprint and token version, which silently logged out the
first browser on its next request. A user could not tell where they were signed in, and there was
no way to close a session left open on a shared computer.

The JWT filter already looks sessions up by `(email, device id)`, and access tokens carry the
device id, fingerprint and version claims, so validation was per-device all along. Only the
storage and the login/logout lookups assumed one session per user.

## Decision

- **One session per user and device.** V23 drops the unique constraint on `user_devices.user_id`
  and adds a unique index on `(user_id, device_id)`. `UserDevice.user` becomes `@ManyToOne`.
  - Login finds the row for the user plus the requesting device id, or creates one. Logging in
    again on the same device reuses its row and bumps its token version.
  - Logout closes the session of the requesting device only. A device id with no session for that
    user is still reported as suspicious and rejected, as before.
- **What a session shows.** V23 adds `user_agent` (from the login request) and `created_at` (the
  login time). Neither takes part in security decisions; the fingerprint already covers the
  User-Agent.
- **Endpoints, all for the authenticated user's own sessions:**
  - `GET /api/v1/users/me/sessions` lists sessions that can still refresh: the active flag is
    set, and the refresh token is neither revoked nor expired. They come most recently used
    first, with `current` marking the requesting device.
  - `DELETE /api/v1/users/me/sessions/{id}` closes one. The current session is refused with 409,
    because closing it is a logout, which also clears the refresh cookie. Another user's id is
    404, never 403, so ids cannot be probed. Closing an already closed session is a no-op.
  - `DELETE /api/v1/users/me/sessions` closes every session except the current one.
- **Closing a session** deactivates it and revokes its refresh token, and is audited as
  `USER_SESSION_REVOKED`. The JWT filter rejects an inactive session, so its access tokens stop
  working on the next request rather than at expiry.
- **At most 10 active sessions per user.** The device id is generated by the client, so a client
  sending a new one on every login could otherwise grow `user_devices` without bound. After each
  login, the least recently used sessions beyond 10 are closed and audited with the
  `session_limit` reason.
- **Password change closes the other sessions.** Whoever knew the old password may hold a session
  elsewhere. The session that changed the password stays open.
- **Current session.** It is identified by the device-id header. The JWT filter has already
  checked that header against the device claim of the access token.

## Consequences

- Several browsers can be signed in at once with the same account, which is what users expect.
  Before, the second login silently logged the first one out.
- Reuse detection (ADR-0023) now closes only the device whose token was replayed, not the whole
  account. That is the right blast radius, and the user can close the rest from the sessions
  screen.
- Session rows accumulate per device. Closed rows are kept: they are small, and audit entries
  point at them. Purging old inactive rows can join the retention job (ADR-0015) if it ever
  matters.
- Admin-side session management (an admin closing another user's sessions) is out of scope.
- Two simultaneous *first* logins from the same new device can race on the unique index; the
  loser gets an error and the client's retry succeeds. This is the same hazard the single row had,
  and is accepted.
